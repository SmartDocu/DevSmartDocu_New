d2chat/history/supabase_storage.py는 호출자(라우터)가 만든 사용자 JWT 클라이언트(sb)를 그대로 받아 쓰면서, 코드 주석에 "RLS(auth.uid())가 신원을 보장하므로 별도 인증 검증 없이 전달받는다"고 명시할 만큼 RLS 적용을 전제로 설계돼 있습니다. 그런데 RLS가 꺼져 있어서 get_session_info/get_session_messages/update_session_title/get_snapshot_messages 4개 함수가 sessionuid/shareuid만으로 조회 — Chat 구독 중인 인증된 사용자라면 누구나 session_id(UUID)만 알면 GET /history/{session_id}로 다른 조직/다른 사용자의 채팅 대화 전체를 그대로 읽을 수 있었습니다. GET /snapshots/{share_uid}도 동일 패턴.

d2chat 전체에서 이 6개 테이블을 건드리는 곳이 supabase_storage.py 한 곳뿐이고 전부 사용자 JWT(sb)만 쓴다는 것, service-role 우회 경로나 프론트의 Supabase Realtime 직접 구독 경로가 전혀 없다는 것까지 재확인 후 RLS를 적용했습니다. chat_sessions/chat_qas/chat_favorites는 본인 소유(creator = auth.uid()) 전용, chat_session_shares는 발신자 전용(수신자는 코드상 이 테이블을 직접 안 읽음), chat_session_share_users는 발신자 insert/발신자+수신자 select/수신자만 update, chat_snapshots는 발신자 OR 수신자만 select — 수신자 판별에 신규 헬퍼 함수 is_chat_snapshot_recipient(shareuid) 사용. content_purge.py(서비스/테넌트 삭제 배치)는 전부 service-role이라 영향 없음도 확인.

18개 체크(교차 사용자 차단, update_session_title/get_session_messages처럼 원래 코드에 creator 필터가 없던 함수의 실제 재현, 정당한 발신자/수신자 접근, 무관한 제3자의 chat_snapshots 접근 차단 — 원래 취약점의 정확한 재현+수정 확인, service-role 대조군) 전부 통과.

🔓 미수정 · insight_*(d2insight) — RLS로는 못 고침, 앱 레벨 소유자 검증 누락이 원인

d2insight/db/insight_storage.py는 sb 파라미터 자체를 받지 않고 항상 모듈 전역 service-role 클라이언트(_sc)로만 접근합니다 — RLS를 걸어도 이 코드 경로엔 영향이 전혀 없습니다(service-role은 RLS를 무조건 우회). 라우터(d2insight/chat/router.py)의 _check_owner(token, user_id)는 경로의 user_id가 내 토큰과 일치하는지만 확인하고, 그 session_id/qauid가 진짜 내 것인지는 검증하지 않습니다.

실제 익스플로잇 경로 3개 확인: ① GET /insight/history/{내_user_id}/{남의_session_id} — _check_owner는 내 user_id라 통과, get_session_messages(session_id)는 소유자 필터가 없어 남의 대화 이력 전체가 그대로 반환됨. ② POST /insight/favorite/qa(body.qauid) — get_qa(qauid)에 소유자 필터가 없어 남의 qauid를 넣으면 그 질문/답변 내용이 내 즐겨찾기로 복사되어 유출됨. ③ 정기 보고서 등록(_resolve_schedule_origin → get_qa(qauid)) — 같은 방식으로 남의 보고서를 내 정기 보고서로 등록 가능. (반대로 delete_session/remove_favorite_qa는 SQL에 .eq("creator", creator) 필터가 있어 안전함을 확인.)

수정 수단은 SQL이 아니라 d2insight/db/insight_storage.py의 Python 코드 — get_session/get_session_messages/get_qa(즐겨찾기·정기보고서 등록 경로)에 호출자의 creator/tenantid 일치 검증을 추가해야 함. RLS는 이 앱의 실제 접근 경로엔 영향이 없으므로(방어심층 목적으로는 걸어둘 수 있음) 이 취약점 자체의 수정 수단은 아닙니다.

"chat_* 적용 완료 후 지금까지 작업한 사항 전체를 RLS뿐 아니라 앱 레벨 권한 체크까지 다시 검증해달라"는 요청으로, 이번 세션에서 만든 검증 스크립트 24개(RLS 15개 + 앱 레벨 권한 체크 6개 + 테넌트 해지/회원 탈퇴/Ch·In 콘텐츠 purge cascade 3개)를 전부 재실행했습니다. 251개 체크 전부 통과, 회귀(regression) 0건. 3개 스크립트(test_rls_doc_pipeline.py/test_tenant_cancel.py/test_tenant_users_authz_fix.py)가 Windows 콘솔 인코딩(cp949가 em-dash 등 일부 문자 출력 실패) 문제로 중간에 멈췄으나, 이건 실제 실패가 아니라 인코딩 설정 문제라 PYTHONIOENCODING=utf-8 강제 후 재실행해 끝까지 확인 — 3개 다 정상 통과.

범위: 이번 세션 전체에서 만든 RLS 정책(49개 테이블, chat_* 6개 포함) + 애플리케이션 레벨 권한 체크(org.py/whitelists.py/connectors.py/llmkeys.py/settings.py/datasets.py/docgroups.py 등) + 워커 service-role 전환 패턴(옛 패턴은 여전히 차단, 새 패턴은 정상 동작) + 테넌트 해지·회원 탈퇴·Ch/In 콘텐츠 purge cascade 흐름(전제조건 차단, 매니저 탈퇴 차단, 최종 잠금, 감사로그, 알림). 새로 발견된 문제는 없습니다.

남은 작업 — rls-audit.html 기준 "적용 권장" 47개를 전부 처리했습니다: 49개 완료(핵심 아이덴티티 10 + 실시간 4 + 문서파이프라인 11 + 항목/콘텐츠 정의 6 + 마스터 데이터 소스 12 + chat_* 6) + 1개 재분류(prompts→적용 불필요). insight_*는 애초 "결정 필요" 등급이었지만 이번 조사로 RLS와 무관한 별도의 실제 앱 레벨 취약점(d2insight/db/insight_storage.py의 소유자 검증 누락 — get_session/get_session_messages/get_qa 경유)이 새로 확인되어 아직 미수정입니다 — RLS가 아니라 Python 코드 수정이 필요해 별도 착수가 필요합니다. 그 외 "결정 필요" 나머지 43개는 대부분 결제/구독/크레딧, 감사·시스템 로그 등 service-role 전용이라 RLS를 걸어도 이 앱의 실제 접근 경로는 안 바뀌는 방어심층 성격의 항목들이라, 우선순위는 낮게 보는 게 맞습니다.

이번 작업에서 두 번(accounts/tenants)이나 "RLS를 걸고 나서야 실제 코드 접근 패턴과의 불일치가 드러났다"는 점, 문서생성 파이프라인의 데이터 품질(NULL 컬럼)과 워커의 부분 payload upsert, 그리고 datas 뷰의 security_invoker 누락까지 겹쳐서 터졌던 점을 감안하면, 앞으로 RLS를 걸 때는 매번 (1) 실제 화면이 어떤 클라이언트(sb vs svc)를 쓰는지, (2) 그 화면이 관리 전용인지 일반 멤버도 쓰는지(조회/쓰기 권한 레벨이 다를 수 있음), (3) RLS 조건에 쓰려는 컬럼의 실제 데이터 품질(NULL 비율)이 어떤지, (4) upsert처럼 부분 payload를 쓰는 곳이 있는지, (5) 뷰가 있다면 security_invoker가 설정돼 있는지 — 이 5가지를 먼저 확인하는 절차를 유지할 것. 2026-09-08 조사에서 얻은 교훈: RLS(DB 레벨)만 감사해서는 안 되고, 애플리케이션 레벨 권한 체크 자체가 통째로 빠진 라우터가 있는지도 주기적으로 훑어야 한다 — 이번에 찾은 6개는 전부 RLS 감사표(rls-audit.html)의 "결정 필요"/"적용 불필요"에 걸쳐 있어 RLS 관점만으로는 절대 못 찾았을 것들이다.
